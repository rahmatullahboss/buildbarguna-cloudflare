## 2025-03-10 - Timing Attack in User Enumeration
**Vulnerability:** Timing attack in the `login` and `forgot-password` endpoints allowing user enumeration.
**Learning:** If an account was not found, the response was immediately returned. If found, a slow PBKDF2 hash verification was performed, or an email was sent synchronously. This time difference allowed attackers to identify registered accounts.
**Prevention:** Always verify a dummy hash to maintain constant-time execution if a user is not found. Use background execution (like `c.executionCtx.waitUntil()`) for slow asynchronous side-effects (e.g., sending emails) so the response isn't blocked.
## 2025-03-09 - TOCTOU Race Condition in Cloudflare D1 Batch Operations
**Vulnerability:** A Time-of-Check to Time-of-Use (TOCTOU) vulnerability existed in company fund withdrawal approvals because `UPDATE` queries lacked strict state checks (e.g., `AND status = 'pending_approval'`) and were bundled into `c.env.DB.batch()` along with audit log insertions.
**Learning:** In Cloudflare D1, `c.env.DB.batch()` executes all statements unconditionally and does not short-circuit if a preceding `UPDATE` fails or affects 0 rows. This means if multiple admins concurrently approve a transaction, the `UPDATE` query might affect 0 rows (as it was already updated), but the subsequent `INSERT` for the audit log will still execute, creating corrupted and misleading audit trails.
**Prevention:** To safely handle state transitions, database operations must be split: execute the conditional `UPDATE` query individually using `.run()` (enforcing the expected previous state in the `WHERE` clause), verify `meta.changes > 0`, and only then execute the subsequent audit log or side-effect statements.
